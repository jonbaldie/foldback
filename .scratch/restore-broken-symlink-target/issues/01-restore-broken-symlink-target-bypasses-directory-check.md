# `restore` into a broken symlink target bypasses directory validation and crashes mid-restore

Found by runtime-instrumented and action-sequence testing, 2026-09-11 (foldback 0.1.0.0, commit 53e78c7, macOS/APFS, normal build).
Evidence: `/tmp/foldback-finding-bugs-20260911/` (report: `report.md`, replay logs `repro-broken-symlink-{1,2,3}.txt`, script `repro-broken-symlink-target.sh`).

## User impact

When restoring a snapshot to a target location that exists as a broken (dangling) symbolic link, `restore` fails to reject the target during `prepareTarget`.

Instead of cleanly rejecting the target before touching data (e.g. `restore target is not a directory: ...`), `prepareTarget` exits 0 without creating a real directory. Subsequent file restoration operations attempt to write through the dangling link, failing mid-restore with cryptic temporary-file errors:
```text
copyFile:atomicCopyFileContents:withReplacementFile:openFdAt: does not exist (No such file or directory)
```

In contrast, restoring into an existing regular file correctly stops early with:
`user error (restore target is not a directory: ...)`.

## Expected vs actual

- **Expected**: `prepareTarget` inspects the target path without dereferencing (or detects dangling symlinks), refusing the broken symlink up front with `restore target is not a directory: <target>`.
- **Actual**: `prepareTarget` passes because `doesPathExist` returns `False` for broken symlinks; `createDirectoryIfMissing` fails to create a directory over the existing symlink, and the command crashes midway through file copying.

## Grounding

In `src/Foldback/Repository.hs:377-385`:

```haskell
prepareTarget :: FilePath -> IO ()
prepareTarget target = do
  exists <- doesPathExist target
  if exists
    then do
      isDirectory <- doesDirectoryExist target
      unless isDirectory (ioError (userError ("restore target is not a directory: " <> target)))
      contents <- listDirectory target
      unless (null contents) (ioError (userError ("restore target is not empty: " <> target)))
    else createDirectoryIfMissing True target
```

In `System.Directory`, `doesPathExist` follows symbolic links (POSIX `stat`). For a dangling symlink, `stat` fails with `ENOENT`, so `exists` is `False`.

`prepareTarget` proceeds to `createDirectoryIfMissing True target`. `createDirectory` fails with `EEXIST` (because a filesystem node named `target` already exists), but `createDirectoryIfMissing` catches the error, checks `doesDirectoryExist` (which is `False`), and returns without throwing.

`prepareTarget` returns successfully. Then `restoreEntry` calls `copyFile object (target </> path)`. Because `target` points to a non-existent path, writing into `target` fails with an internal IO error.

## Fix direction

In `prepareTarget`:
Check for symbolic links explicitly using `pathIsSymbolicLink target` (or `Posix.getSymbolicLinkStatus target`):
```haskell
prepareTarget target = do
  isLink <- pathIsSymbolicLink target
  when isLink (ioError (userError ("restore target is not a directory: " <> target)))
  exists <- doesPathExist target
  ...
```

### Agent Brief

**Category:** bug
**Summary:** Make `restore` refuse a target that exists as a symbolic link (dangling or not) up front, before touching any data

**Current behavior:**
When the restore target path exists as a dangling symlink, the target-existence check follows the link (stat fails, so the path is treated as nonexistent) and the directory-creation step silently does nothing over an existing filesystem node. The restore proceeds and crashes midway through copying files with an internal `copyFile:...does not exist` error, having already written nothing meaningful but also given no clean rejection. Existing regular files as targets are correctly refused up front with `restore target is not a directory`.

**Desired behavior:**
`restore` rejects a target that exists as a symbolic link before preparing or writing anything, with the same class of message as other invalid targets (e.g. `restore target is not a directory: <target>`) and a non-zero exit. This covers both dangling symlinks and symlinks pointing at real directories — a symlink is not accepted as a target regardless of what it points to. Behavior for regular files, empty directories, and missing paths is unchanged.

**Key interfaces:**
- The restore-target preparation function in the repository module (currently: existence check, directory check, non-emptiness check, else create): add a lstat-style symlink check that does not follow the link, ahead of the existence check. The equivalent lstat capability is already used elsewhere in the module for the backup source check.
- No change to `restoreEntry` or the copy mechanics.

**Acceptance criteria:**
- [ ] Restoring into a dangling symlink fails before any files are written, with a clear `not a directory`-class error and non-zero exit
- [ ] Restoring into a symlink pointing at a real directory is also refused (same message class), rather than restoring through the link
- [ ] Restoring into a regular empty directory, a missing path, and a regular file behaves exactly as before
- [ ] Existing tests pass; new tests cover both dangling and valid symlinks as targets

**Out of scope:**
- Following symlinks and restoring through them
- Changes to backup source handling or repository-layout checks
